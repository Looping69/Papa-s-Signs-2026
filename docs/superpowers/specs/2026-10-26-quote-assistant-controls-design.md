# Quote assistant admin controls

## Intent and decisions
Give staff control over the public Smart Quote Assistant, service-specific pricing, and response gates. The user confirmed that every estimate requires staff approval; nothing generated by the assistant is a binding quote.

## Approaches
Editable prompts alone cannot enforce prices or the disabled state. The recommended server-enforced approach was presented: server-owned rates and calculations, controlled response paths, and a master availability switch. The user confirmed the mandatory staff-approval requirement. A complete CRM, payment flow, or automated binding quotation system is not required.

## Proposed behavior
- Add a Quote Assistant area in the existing admin, using its visual system and explicit Save All Changes behavior.
- Master enabled switch: off hides assistant navigation and launch controls, prevents direct-route interaction, and rejects quote requests at the server. Ordinary staff contact channels remain available.
- Per-service controls: enable automated estimation, pricing basis (per item, per square metre, fixed package), rate in ZAR, package quantity where applicable, minimum charge, and required specification fields. Validate finite non-negative values and explicit units. Do not invent default VAT, installation, design, delivery, or discount rules.
- Gate incomplete specifications with targeted questions. Unsupported services, custom specifications, missing rates, conflicting inputs, and requests for discounts or delivery guarantees go to staff instead of receiving invented prices.
- Compute prices deterministically on the server from saved rates and validated specifications. User messages and AI output cannot change rates or mark anything approved. Do not expose internal prompts or secrets in responses.
- Every estimate visibly states that staff must review specifications and confirm the final quote. It is not an invoice, an accepted order, or evidence of staff approval.
- Provide controlled messages for missing details, unsupported requests, unavailable service, temporary failure, and staff handoff. Mandatory disclaimers and boundaries cannot be removed through message customization.
- Keep staff review manual through existing contact channels in this phase. Do not imply that an estimate was sent, stored in an approval inbox, approved, emailed, or assigned unless a real workflow implements and verifies that action.

## Architecture and security
Reuse the existing React/Express application and configuration storage. Establish the quote API request/response contract before implementation. Keep any existing Gemini integration server-side with its configured provider; the model may assist with interpretation, never authoritative arithmetic or approval. Invalid/unavailable configuration fails closed to staff handoff. Bound input lengths, request frequency, execution time, and conversation context.

The existing admin/config-write/upload routes have no verified staff authentication. Real staff authorization for sensitive controls is required before exposing this publicly; adding an enable switch does not secure those endpoints. Do not silently claim a production security guarantee or deploy the feature without resolving that boundary.

## Verification
Test configured rates, quantity/area units, missing specifications, malformed and extreme values, unsupported requests, prompt-injection attempts, absence of binding-price claims, disabled server requests, hidden entry points, failed provider calls, and saved configuration persistence. Verify the actual browser flow, TypeScript checks, and build. Report which guarantees were demonstrated locally and what remains blocked for production.

## Approval
Written design approved by the user on 26 October 2026 together with the media-library design. The initial implementation uses guided specifications without model calls; no browser model credentials or model-generated prices are used.
